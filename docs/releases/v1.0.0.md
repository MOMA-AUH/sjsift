# sjsift v1.0.0 release notes

This is the prepared source for the first stable sjsift release.
Candidate validation and publication remain separate release gates.
These notes do not announce an available tag or package.
[Issue #74](https://github.com/MOMA-AUH/sjsift/issues/74) tracks candidate validation.
[Issue #75](https://github.com/MOMA-AUH/sjsift/issues/75) tracks publication and the
clean installation of the published package.

## Changes since v0.2.2

The [stable v1 compatibility contract](../COMPATIBILITY.md) applies from v1.0.0.
It protects accepted invocations, pinned schema-3 inputs, exact matching, both
TSV formats, provenance schema 1, and documented offline HTML capabilities throughout v1.
Internal Python imports and HTML markup are outside the supported public interface.
Existing v0.x releases retain their historical pre-1.0 policy, including possible
breaking changes in patch releases. They acquire no retrospective guarantees.

The release adds optional `--provenance-output PATH` for deterministic JSON.
It records exact catalog and STAR fingerprints, sample selection, warnings,
dependency versions, and completed alignment and CRAM reference checks.
Both TSV formats remain unchanged when provenance is requested.
The [provenance guide](../PROVENANCE.md) defines fields and retained metadata.

Shared alignment records now retain transcript-strand evidence for each qualifying
junction membership. Read labels exclude ineligible memberships and distinguish
agreeing from unverified evidence, including mixed evidence on one physical record.
The legend separates mapping patterns from support colors and explains gold
soft-clip blocks and hard-clip diamonds. The report presents concise input facts.
These display changes preserve STAR support and the complete eligible-record inventory.

A closed stdout pipe now produces the documented status `2` without a second
shutdown error or traceback. Failed report writes remove newly created files
where possible and preserve existing destinations.

Source distributions now include the fixtures and policy inputs needed to build
and test the extracted archive independently. Required CI also exercises installed
wheel reports in Chromium and real STAR BAM/CRAM fixtures. The release includes
documented capacity measurements and an independent report-readiness auditor.
The auditor now checks the current structured provenance facts.

## Installation, pinned catalogs, and migration

After publication, install the exact application version and retain its catalog:

```bash
conda create --name sjsift-v1 --channel conda-forge --channel bioconda MOMA-AUH::sjsift=1.0.0
conda activate sjsift-v1
curl -L --fail \
  https://raw.githubusercontent.com/MOMA-AUH/sjsift/v1.0.0/definitions/grch38.toml \
  -o grch38-v1.0.0.toml
sha256sum grch38-v1.0.0.toml
sjsift --version
```

The catalog SHA-256 is
`a532f7bf56618991d403d7b3c87fc2d398d4203695b127caab68e8874c557ba3`.
Before publication, use the source checkout with the
[development installation instructions](../DEVELOPMENT.md#local-setup).

Existing v0.2.2 invocations and schema-3 catalogs need no input migration.
The required sample-name rules and explicit indexed CRAM reference remain unchanged.
Schemas 1 and 2 remain unsupported. The upgrade never replaces a user's catalog.
Retain application and catalog versions together when reproducing earlier runs.
For example, this existing invocation remains valid:

```bash
sjsift --sample-name sample-01 --junctions sample.SJ.out.tab \
  --definitions grch38-v1.0.0.toml --output sample.tsv
```

To also record provenance, use a new destination for each output:

```bash
sjsift --sample-name sample-01 --junctions sample.SJ.out.tab \
  --definitions grch38-v1.0.0.toml --output sample-with-provenance.tsv \
  --provenance-output sample.provenance.json
```

Development snapshots after v0.2.2 briefly emitted an earlier schema 1.
Their assurance fields and alphabetical key order are outside the stable baseline.
Snapshot consumers must adopt the structured fields and fixed serialization order
in [PROVENANCE.md](../PROVENANCE.md#schema-version-1).
These pre-release revisions did not change a previously published stable format.
No migration applies to JSON from published v0.2.2 because that release had no provenance option.

## Supported environment and capacity

Python 3.11 or newer is required. Linux CI tests Python 3.11–3.14, including
installed Python and Conda packages. Python metadata has no upper version bound.
Future Python versions require validation before support is claimed.
The runtime dependency remains `pysam>=0.24.0,<0.25`, with 0.24.0 tested on Python 3.11.
No additional operating-system or browser-version matrix is promised.
Reports open through `file:` URLs without a server, network, or original input files.
Counts, details, and native read inspection remain readable without JavaScript.
Interactive filters and paging require JavaScript.

The [capacity baseline](../CAPACITY.md) completed every check at 10,000 eligible
records in both synthetic scenarios and both BAM/CRAM formats.
This is an environment-specific tested envelope, not a universal limit.
The benchmark used Linux, Python 3.14.7, pysam 0.24.1, headless Chromium,
and a one-million-base synthetic reference. Python workers had a 2,048 MiB budget.
The browser process tree had a 4,096 MiB budget, with 30-second opening and
10-second interaction limits. Larger cases exceeded interaction or memory budgets.
Paging retains all embedded evidence and does not reduce file size or initial memory.

Those measurements describe the recorded 2026-11-04 source, not a newly measured v1.0.0 artifact.
The [historical readiness record](../RELEASE_READINESS.md) also identifies an earlier candidate.
The v1 candidate gate must distinguish retained capacity evidence from rerun report,
provenance, inventory, offline-browser, and full-reference CRAM measurements.

Version classification: v1.0.0 establishes the first stable major baseline.
Relative to v0.2.2, optional provenance is an additive feature. Strand labels and
closed-pipe handling are fixes. Legend changes affect presentation.
Packaging and validation changes add release evidence.
No existing invocation, schema-3 input, TSV format, or supported runtime is removed.
Future changes must follow the contract's patch, minor, major, and deprecation rules.
